# House Mix Offline First — database per radio

## Decision and scope

Each radio/customer receives an independent PostgreSQL database on its designated primary server. Authorized workstations for that same radio connect to the same primary service and therefore use the same customer database. A workstation must never create or select its own competing copy of the customer database.

Different radios on the same Windows administrator computer remain isolated by their client workspace and by separate database identities. The Electron profile is not the database boundary: the primary server is authoritative for the radio's shared data.

This document defines the next implementation contract. It does not provision databases, start PostgreSQL, migrate customer data, open LAN ports, or change production.

## Required topology

Use two logical database layers on the primary server:

1. **Control-plane catalog** — small service database for tenant identity, device enrollment, device status, and the mapping from an authenticated tenant to its database identifier. It contains no radio programming/business records.
2. **One data database per radio** — contains that radio's application data, sync outbox/inbox, audit events, and migration ledger. No application rows from another radio may be stored here.

The existing prototype schema currently places tenant/device control-plane tables and sync tables together. It is a prototype, not yet the final per-radio topology. Split it deliberately in a reviewed migration; do not copy the existing SQL into production unchanged.

## Identity and routing rules

- Authenticate a device against the control-plane catalog before selecting a customer database.
- Resolve the tenant/database mapping only from the authenticated device record. Never accept a database name, tenant slug, schema name, or connection string from a request body, query parameter, or renderer.
- Use a strict allow-listed database identifier generated by the server. Never interpolate user-controlled identifiers into SQL.
- Keep database credentials and connection strings on the primary server only. A workstation receives an authenticated API identity, never PostgreSQL credentials.
- Maintain one bounded connection pool per active customer database. Enforce pool limits and idle eviction; never create an unbounded pool per request.
- A missing, suspended, archived, or ambiguous tenant mapping fails closed.
- The same tenant's workstations must resolve to the same primary database. Do not create a new database when a workstation pairs.

## Provisioning contract

Provisioning is an explicit administrator operation on the primary server:

1. Validate and normalize the radio's immutable tenant ID.
2. Reserve the database identifier in the control-plane catalog under a transaction/unique constraint.
3. Create the database using a server-generated identifier and least-privilege database owner.
4. Apply versioned migrations and record checksums in that database's migration ledger.
5. Verify required extensions, tables, indexes, constraints, and database ownership.
6. Mark the mapping active only after all checks pass.
7. On any failure, leave the mapping inactive and emit an auditable error. Never silently point the tenant at another database.

Provisioning must be idempotent: rerunning it must verify and resume a known incomplete operation, not overwrite an existing database.

## Backup and standby contract

- Back up each radio database independently, plus the control-plane catalog.
- Every backup records tenant ID, database ID, schema version, timestamp, checksum, and backup format.
- Restore into an isolated temporary target, verify checksum and schema, then require an explicit operator promotion.
- Standby replication/failover is per primary-server installation and must preserve the tenant-to-database mapping. A standby must not become writable merely because it starts.
- Never treat a folder copy of a live PostgreSQL data directory as a valid backup.
- Retention, encryption-at-rest, off-machine copies, restore drills, and RPO/RTO targets must be specified before customer rollout.

## Isolation acceptance tests

- Radio A and Radio B resolve to different database identifiers and connection pools.
- Two devices enrolled to Radio A resolve to the exact same database identifier.
- A client cannot choose or override its tenant/database through any request field.
- Revoked or suspended devices cannot access a tenant database.
- A missing mapping, failed migration, or failed health check blocks activation.
- A backup from Radio A cannot be restored or registered as Radio B without an explicit, audited migration workflow.
- Connection-pool limits remain bounded when many radios are active.
- No customer database is exposed directly to the LAN; only the authenticated local API may be reachable after the security gate is approved.

## Migration boundary

No existing customer data is eligible for migration until an authoritative fresh export is inspected, the current schema and storage objects are inventoried, tenant ownership is proven, ambiguous rows are quarantined, and a dry-run report is reviewed. Do not infer tenant ownership from names, email addresses, or UI labels.

## Explicit non-goals

This design does not enable LAN access, change the existing web application, connect Lovable Cloud or Supabase, create customer databases, migrate production records, or activate automatic failover.
